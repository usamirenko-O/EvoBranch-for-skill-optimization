# Paper-to-code mapping (Phases 1–3)

Source: Peng, Yang, Fu, Zhang, Zhang, Zhao, Su, Wu, Li, Zhu, Zhao, Lei,
"Self-Supervised Skill Optimization", arXiv:2607.28777v1 [cs.CL], 30 Jul 2026.
References below are to that paper's Methodology section, Algorithm 1, and
equations (1)-(18). The paper's cited "supplementary material" (exact
prompts, per-dataset schedules, dataset details) is not part of the arXiv
PDF and was not available when writing this mapping.

Phase 1 implements **only** the deterministic core: the data model behind
behavior extraction/clustering outputs, and the Evidence Aggregation and
Ranking step (eq. 9-14). It does not implement `f_gen`, `f_judge`, `f_beh`,
`f_cluster`, `f_render`, the outer training loop, or any sampling policy.

Every row is marked:
- **PAPER_SPECIFIED**: directly implements a stated equation/rule.
- **REPRODUCTION_CHOICE**: fills a gap the paper leaves open; see
  `docs/assumptions.md` for the reasoning and how to change it.

## Probes vs. the rendered candidate (terminology note)

The paper draws a hard line between two different objects that are easy to
conflate:

- A **probe** `P_k` (eq. 3-4) is one of `K` exploratory skill variants
  generated by `f_gen` at step `t`. Probes are only ever used to *produce
  executions to compare against the anchor* (eq. 4-5) and, downstream, to
  *expose behavioral differences* (eq. 6). "The probes serve only to expose
  alternative behaviors and are never accepted directly."
- The **candidate skill** `S~_{t+1}` (eq. 15) is produced by `f_render` from
  the aggregated, ranked behavior units `U_t` -- it is a fresh whole-skill
  document that "can combine supported behaviors from different probes and
  need not match any individual probe." Only the candidate (never a probe)
  is subject to the validation gate (eq. 16-18) and can become `S_{t+1}`.

`sso/core/types.py` reflects this: `ExecutionRef.probe(...)` is documented as
identifying a probe execution specifically, and `BehaviorUnit` (the output of
Phase 1's pipeline, i.e. `U_t`) is documented as the *input* to `f_render`,
not a skill itself. No type in Phase 1 represents `S~_{t+1}` or the
validation gate, since rendering and validation are later phases.

## `sso/llm/` (Phase 2a interfaces)

Phase 2a defined **only** the five LLM-backed modules' interfaces (abstract
base classes and their input/output types) -- no prompts, no network/SDK
calls, no OfficeQA or execution harness, no outer loop, no validation gate.
`sso/core/evidence.py` (Phase 1) is unchanged. The following table records
the reviewed interface contracts; concrete implementations are mapped below.

| Module (paper element) | File | Status |
|---|---|---|
| `ProbeGenerator` (`f_gen`, eq. 3-4) | `sso/llm/probe_generator.py` | PAPER_SPECIFIED for the output contract (K complete skills, each distinct from `S_t` and its peers); PAPER_SPECIFIED for `history` (`H_t`)'s *shape* -- see correction below; REPRODUCTION_CHOICE for `H_t`'s *selection policy* (unspecified, deferred to `sso/sampling.py`) |

### Correction: `H_t`'s type (eq. 3)

An earlier, uncommitted draft of `ProbeGenerator` typed `history` as
`Sequence[BehaviorUnit]`, guessing that `H_t` meant previously-selected
behavior units from earlier optimization steps. The paper's eq. 3 pins this
down directly: `Ht ⊆ {(xi, r_i^o) | xi ∈ Xt}` -- a subset of (task,
anchor-execution) pairs from the *current* step's training batch. Phase 2
corrects `history` to `Sequence[Tuple[Task, Execution]]` accordingly. Only
*which* pairs make up that subset remains an open REPRODUCTION_CHOICE (same
status as `X_t`/`V_t` selection, above).

## Phase 2b concrete implementations

Source rechecked before implementing each module: [original v1 Methodology
and Algorithm 1](https://arxiv.org/html/2607.28777v1). The v1 HTML has no
appendix section or exact module prompts; its Implementation Details refers
those prompts to supplementary material. We have not recovered that material.
These are faithful interface implementations, not a claim of exact prompt or
experimental reproduction. The paper reports GPT-5.5 for all five optimizer
modules; the client requires an explicit model rather than substituting one.

The five reviewed ABCs and their method signatures remain unchanged.
Concrete subclasses live alongside them; no Phase 1 core files were edited
for Phase 2b. No execution, sampling, validation gate, or outer loop was added.

| Concrete class / helper | Paper source rechecked | PAPER_SPECIFIED behavior | REPRODUCTION_CHOICE implementation |
|---|---|---|---|
| `LLMPairwiseJudge` | eq. 5; Algorithm 1 line 9; eq. 17 discussion | Randomize execution presentation and remap preference to semantic `y` | Injected `random.Random`, anonymous A/B content, exact prompt, strict decision JSON |
| `LLMProbeGenerator` | eq. 3–4; Algorithm 1 line 6 | Joint generation of exactly K complete distinct exploratory skills from current skill and task/anchor history | Ordered document JSON; 1-based indices; whitespace-insensitive textual duplicate rejection |
| `LLMBehaviorExtractor` | eq. 6–7; Algorithm 1 lines 12–13 | All executions together; descriptions and complete activation mappings; no judge outcomes | Execution aliases, deterministic local record ids, string activation JSON; malformed mappings rejected |
| `LLMBehaviorClusterer` | eq. 8; Algorithm 1 line 15 | Description-only clustering; full partition; original member representative; distinct behaviors separate | Id-only JSON, partition validation before constructing assignments |
| `LLMRenderer` | eq. 15; Algorithm 1 lines 32–35 | Whole candidate from current skill and selected evidence; direction constraints; no unsupported opposite | Evidence-field JSON and full-document response; empty input raises caller error |
| `LLMClient`, `ChatCompletionsClient` | No specified transport | Fixed judge model is a caller responsibility | Synchronous text protocol; optional standard-library Chat Completions HTTP adapter |
| `_structured.py` | No specified wire schemas/parsing | Checks preserve required type and coverage constraints | Strict JSON; no coercion, repair, retry, or missing-state fallback |

`assemble_clusters` is unchanged and remains outside the LLM stage. Call it
with validated assignments and the original records. Its existing general
helper does not validate arbitrary externally supplied partitions; the
concrete clusterer now validates its own output before returning it.

Semantic equivalence, whole-skill completeness, behavioral accuracy, and
unsupported-opposite avoidance are requested in prompts but cannot be proven
by structural validation. The renderer has no probes as input and therefore
cannot check candidate equality against probes. The paper says a candidate
need not match a probe, not that accidental textual equality is prohibited.
The Phase 2a wording about being distinct describes provenance; Phase 2b
does not add an inequality filter or a regeneration policy.

### Using the concrete modules

All network calls go through `LLMClient.complete(system=..., user=...)`.
Here is explicit configuration for an endpoint supporting Chat Completions
JSON-object mode. These environment variable names are example application
configuration, not automatically read by the library:

```python
import os
import random
from sso.llm import (
    ChatCompletionsClient, LLMPairwiseJudge, LLMProbeGenerator,
    LLMBehaviorExtractor, LLMBehaviorClusterer, LLMRenderer, assemble_clusters,
)

client = ChatCompletionsClient(
    endpoint=os.environ["SSO_CHAT_COMPLETIONS_URL"],  # full URL, including path
    model=os.environ["SSO_MODEL"],
    api_key=os.environ.get("SSO_API_KEY"),
)
judge = LLMPairwiseJudge(client, rng=random.Random(42))  # example replay seed
generator = LLMProbeGenerator(client)
extractor = LLMBehaviorExtractor(client)
clusterer = LLMBehaviorClusterer(client)
renderer = LLMRenderer(client)

# Given task, anchor_execution, and all probe_executions from a caller:
# records = extractor.extract(task, anchor_execution, probe_executions)
# assignments = clusterer.cluster([(r.record_id, r.description) for r in records])
# clusters = assemble_clusters(assignments, records)
```

The adapter follows the [Chat Completions API format](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).
Compatible endpoints must accept system/user messages and JSON-object mode.
Other providers can implement the two-string client protocol without changing
module logic. No live provider was invoked or model availability verified.

## Phase 3 execution and orchestration

Rechecked the original [v1 Methodology, Algorithm 1, and eq. 1–18](https://arxiv.org/html/2607.28777v1)
before implementation. Phase 3 adds the generic execution boundary, a complete
optimization step, the exact validation gate, and a finite explicit-schedule
loop. Existing core types, evidence math, and all Phase 2 code are unchanged.

| Implementation | Algorithm 1 / equations | PAPER_SPECIFIED behavior |
|---|---|---|
| `Executor.execute(skill, task)` | eq. 1 | Skill and task produce an observable execution |
| `SSOOptimizer.step`: anchors and history | lines 3–6; eq. 2–3 | Execute current skill; history pairs refer to current-batch anchors; jointly generate K probes |
| Probe execution and judging | lines 7–10; eq. 4–5 | Run every probe on the same tasks; compare to the matching reused anchor |
| Extraction and clustering | lines 12–15; eq. 6–8 | Only decisive tasks; all K executions together; no outcomes to extractor; only descriptions and bookkeeping ids to clusterer |
| `assemble_clusters`, `compute_behavior_units` | lines 17–30; eq. 9–14 | Reattach original records; use unchanged evidence normalization, aggregation, ranking and budget |
| Empty-unit branch | lines 32–34 | Retain current skill; skip rendering and validation entirely |
| Rendering | line 35; eq. 15 | Create a candidate from current skill and aggregated behavior units |
| `validate_candidate` | lines 36–42; eq. 16–18 | Execute both skills with the same executor; use the same judge; accept iff candidate wins exceed losses; ties count in neither |
| `SSOOptimizer.optimize` | lines 1, 43–45 | Carry selected skill across T iterations and return S_T |

REPRODUCTION_CHOICE details are in assumptions §§15–18: ABC shape, reference
binding, explicit task-id history membership, sequential scheduling, boundary
checks, trace records, and the finite per-step input schedule. No X/H/V
selection policy is implemented. `StepInputs` receives already selected tasks
and history task ids; the optimizer materializes those ids into fresh pairs.
This version supports precomputed history membership, not an internal
content-based selector. Validation tasks are supplied upfront but executed
only after a nonempty update is rendered.

### Validation reference compatibility

The Phase 2 judge already documents reuse for eq. 17 but requires a positive
`probe_index` and a non-anchor `ExecutionRef`. Phase 3 uses a local comparison
slot of 1 for the candidate. This is only an adapter alias, not an exploratory
probe or a promotable probe skill. `ValidationComparison` names current and
candidate roles explicitly and stores y rather than leaking a training
`PairwiseDecision` into the evidence pipeline. Training and validation
executions/results are kept in separate containers; references are scoped to
their step and phase. The existing judge handles randomization/remapping in
both phases unchanged.

### API usage with caller-owned components and selections

```python
from sso.core.algorithm import SSOOptimizer, StepInputs
from sso.core.validation import validate_candidate
from sso.executors import Executor

# Components and selected inputs below are supplied by the caller.
optimizer = SSOOptimizer(
    executor=executor, generator=generator, judge=judge,
    extractor=extractor, clusterer=clusterer, renderer=renderer,
    num_probes=3, update_budget=4,
)
inputs = StepInputs(
    training_batch=training_tasks,
    history_task_ids=selected_history_task_ids,
    validation_batch=validation_tasks,
)
step_result = optimizer.step(current_skill, inputs)
next_skill = step_result.selected_skill
# step_result.validation is None when behavior_units is empty.

# Alternatively, run an explicitly precomputed sequence; T = len(schedule).
run_result = optimizer.optimize(initial_skill, preselected_schedule)
final_skill = run_result.selected_skill
```
